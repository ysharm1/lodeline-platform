# Business model update, 18 October 2026

This page explains every change in this update, step by step, in plain
language. For the reasons behind the model itself, read
[`business-model.md`](business-model.md) first.

Each step says: **what changed**, **why**, **where it lives** in the code, and
**how to check it**.

---

## Step 1. One file for all prices

**What changed.** All prices and business rules now live in
`src/services/pricing.ts`: pack tiers, supplier verification fees, refresh plan
prices, the commissions switch, and the payment disclosure text.

**Why.** Before, there was one pack price set by an environment variable. Now
there are several products. Keeping every number in one file means anyone can
change a price without hunting through the code.

**Where.** `src/services/pricing.ts`. The old `PACK_PRICE_CENTS` and
`STRIPE_PRICE_PACK_STANDARD` settings are removed from `.env.example`,
`render.yaml` and the README.

**How to check.** `src/services/pricing.test.ts` checks every tier, fee and
rule.

---

## Step 2. Database changes

**What changed.** One new migration:
`prisma/migrations/20261018090000_business_model/migration.sql`.

| Change | Plain meaning |
|---|---|
| `EvidencePack.tier` | Each pack remembers whether it was sold as Starter, Standard or Custom. Existing packs are marked Starter. |
| `SupplierRequest.reuseConsentAt`, `reuseConsentName`, `reuseConsentWithdrawnAt` | When a supplier allowed reuse, who agreed, and when they withdrew it. |
| `SupplierRequest.packId` is now optional, plus a new `verificationId` | A document request can now belong to a supplier's own verification, with no buyer. |
| Check constraint `SupplierRequest_one_owner_check` | The database refuses a request that belongs to both or neither. |
| New table `SupplierVerification` | One row per paid supplier review. |
| New table `RefreshSubscription` | One row per buyer refresh plan. |

**Why.** The new products need somewhere to record what was sold and to whom.

**How to check.** The migration was applied on a clean Postgres 16 after all
earlier migrations. A test insert of a request with no owner was refused, as
intended.

## Step 3. Pack tiers (buyer pays)

**What changed.**

1. When a buyer orders a pack, the system counts the flagged parts and the
   distinct supplier names behind them.
2. It picks the smallest tier that fits: Starter ($2,500, up to 5 parts and 3
   suppliers) or Standard ($5,000, up to 15 parts and 8 suppliers).
3. Anything larger is refused with a clear message asking for a quote. The
   request is logged so the team can follow up.
4. When the buyer adds suppliers, the system stops them at the tier's limit.
   Revoking a supplier's link frees a slot.

**What the buyer sees.**

- The audit results page now says, for example: *"Your scope: 4 parts to
  document from 2 named suppliers. That fits the Starter pack: $2,500."*
- The order button names the tier and price.
- For a large list, a **Request a quote** button replaces the order button.
- The pack page shows the tier and "2 of 3 suppliers used".
- The `/pack` page shows all three tiers.

**Where.** `src/services/packs.ts`, `src/services/suppliers.ts`
(`addRequest`), `app/(platform)/audit/[auditId]/page.tsx`,
`app/(platform)/pack/page.tsx`, `app/(platform)/buyer/packs/[packId]/page.tsx`.

**How to check.** Database tests in `src/services/business-model.db.test.ts`
cover a Starter pack, a Standard pack, the quote case, and the supplier limit.

## Step 4. Supplier consent to reuse documents

**What changed.**

1. The supplier upload page (`/s/[token]`) has a new box: **Send these
   documents once**.
2. It explains in plain words that, if the supplier agrees, Lodeline keeps the
   reviewed documents and can use them for that supplier's other customers.
3. It is off by default. To turn it on, the supplier types their name.
4. The supplier can withdraw it on the same page.
5. Both actions are written to the audit log.
6. The admin review queue now shows, for each claim, who it is for and whether
   reuse is allowed.
7. The admin Suppliers page labels each document: *reuse allowed*, *supplier
   verification*, or *one buyer only, cannot verify*.
8. **The rule:** a public directory listing can only be marked verified from
   documents the supplier allowed us to reuse, or from that listing's own paid
   verification. Anything else is refused.

**Why.** Reusing documents is the core of the business. Doing it without
permission would break supplier trust and could expose a buyer's supply chain.

**Where.** `src/services/suppliers.ts` (`setReuseConsent`,
`hasActiveReuseConsent`), `app/api/s/[token]/consent/route.ts` (rate limited
like uploads), `app/(platform)/s/[token]/consent.tsx`,
`src/services/directory.ts` (`verify`).

**How to check.** Database tests cover giving, refusing without a name, and
withdrawing consent, and that verification is refused without it.

**Not done yet.** Copying a consented document into a second buyer's pack is a
manual admin step for now.

## Step 5. Supplier verification (supplier pays)

**What changed.** A new product, run by the team from `/admin/verifications`.

1. **Start.** The admin picks a listing, enters the supplier's email and the
   number of facilities, and clicks **Start verification and email payment
   link**. The fee follows the facility count ($1,500, $3,000 or $5,000 a year).
2. **Payment.** The supplier gets an email with a Stripe payment link. The
   email says the fee covers the review, whatever it finds.
3. **Upload link.** When payment arrives, the review year starts and the
   supplier gets a private upload link (valid 60 days). It asks only about the
   upstream stages the listing says it covers.
4. **Review.** Uploads go through the same checks and the same review queue as
   buyer packs.
5. **Verify the listing (separate step).** If the accepted evidence supports
   it, the admin marks the listing verified on the Suppliers page.
6. **Close.** The admin clicks **Mark review complete**, whatever the result.
7. **Cancel.** An unpaid verification can be cancelled. A paid one can't; refund
   in Stripe if needed.

**The safeguard.** Payment never marks a listing verified. A test reads the
verification code and fails if it ever writes the verified field. Another test
fails if directory order ever depends on payment.

**Also changed.** The `/for-suppliers` page explains verification, its prices,
and the rule "you pay for the review, not the result".

**Where.** `src/services/verifications.ts`, `app/(platform)/admin/verifications/`,
`app/api/admin/listings/[listingId]/verification/route.ts`,
`app/api/admin/verifications/[verificationId]/route.ts`,
`app/(platform)/for-suppliers/page.tsx`.

**How to check.** Database tests walk the whole flow: start, pay, upload link,
listing still not verified after payment, verify from the supplier's own
accepted evidence, complete. They also check underpayment is refused and a
paid verification can't be cancelled.

## Step 6. Refresh plans (buyer pays monthly)

**What changed.**

1. A paid pack page shows **Keep this pack current**, with the monthly price
   ($250 Starter, $500 Standard). Custom packs are quoted.
2. The buyer pays through Stripe as a monthly subscription.
3. When the first payment arrives, the plan becomes active and the first
   re-check is due in 90 days.
4. The new admin page `/admin/refresh` lists plans and highlights the ones due.
5. After re-checking a pack, the admin clicks **Mark refreshed**. The next due
   date moves 90 days out.
6. If the buyer cancels in Stripe, the plan is marked cancelled. It can be
   restarted later.

**Where.** `src/services/refresh.ts`, `app/api/packs/[packId]/refresh/route.ts`,
`app/api/admin/refresh/[refreshId]/route.ts`, `app/(platform)/admin/refresh/page.tsx`.

**How to check.** Database tests cover activation, due dates, admin-only
refresh, cancellation, replayed events, and restarting.

## Step 7. One payment system for everything

**What changed.** Stripe checkout now sells three things. Each payment carries
a label saying what was bought (`pack`, `verification` or `refresh`), and the
webhook sends it to the right place. Payments started before this update only
had a pack id; those still work.

The webhook also listens for cancelled subscriptions, to end refresh plans.

**Where.** `src/infra/billing.ts`, `app/api/webhooks/stripe/route.ts`.

**Action needed in Stripe.** Add the event `customer.subscription.deleted` to
the webhook endpoint, next to `checkout.session.completed`.

**How to check.** `src/services/webhooks.test.ts` checks signed test events of
each kind, plus old-style pack events.

---

## Step 8. No commissions, and a disclosure everywhere

**What changed.**

1. Supplier commissions are switched off in `pricing.ts`
   (`SUPPLIER_COMMISSIONS_ENABLED = false`). A test keeps it that way.
2. `/admin/referrals` now explains why, instead of being an empty placeholder.
3. A short disclosure of how Lodeline is paid appears on the `/pack` page, on
   every buyer pack page, and in the pack PDF.

**Why.** Being paid by suppliers when buyers switch would give us a reason to
find gaps, and could raise Anti-Kickback Act questions. Any referral structure
should be reviewed by a government contracts attorney first.

**Where.** `src/services/pricing.ts`, `app/(platform)/_components/conflict-disclosure.tsx`,
`src/services/pack-pdf.tsx`, `app/(platform)/admin/referrals/page.tsx`.

## Step 9. A link to the free audit on the home page

**What changed.** The home page hero now has a third button, **Run a free parts
audit**, linking to `/audit`. Before, the audit was built but nothing on the
marketing site linked to it.

**How it was done.** The marketing pages are a word-for-word copy of
lodeline.org, guarded by a test. Rather than edit the copy, the port script
(`scripts/port-site.py`) now has a short list of approved **additions**. Each
added element is marked `data-ll-added`. The test sets marked elements aside,
checks the rest still matches lodeline.org word for word, and checks the
additions are exactly the approved ones.

**To add another entry point later:** add one line to `ADDITIONS` in
`scripts/port-site.py`, run `python3 scripts/port-site.py`, and update the
"approved additions" test.

**About the Chinese booking text.** The Traditional Chinese Calendly
instructions are on the live lodeline.org site only. They are not in this
repository: the site snapshot here was taken on 16 October, before they were
added, and the built pages contain no Chinese text. Remove them from the live
site's source directly. If they were meant for the Taiwan lead, put them on a
separate page.

## Deploying this update

1. **Back up the database.**
2. Deploy the code. Run `npx prisma migrate deploy`. It applies one migration.
3. In Stripe, add `customer.subscription.deleted` to the webhook endpoint.
4. Remove `PACK_PRICE_CENTS` and `STRIPE_PRICE_PACK_STANDARD` from the hosting
   settings. They are no longer read.
5. Smoke test with Stripe test keys: order a Starter pack, start a refresh
   plan, and start a verification for a test listing.
